Что такое SQL
и почему он быстрый

Один экран, чтобы понять язык запросов, разницу со старым добрым Excel и почему «колонки» иногда обгоняют «строки».

01 — суть

SQL — это список покупок, а не маршрут

SQL (Structured Query Language) — язык запросов к базам данных. Главная фишка: ты пишешь ЧТО хочешь получить, а не КАК это искать. Такой подход называют декларативным. Сравни два способа отправить ребёнка в магазин 👇

● Декларативно (SQL)

«Что»
Список:
— молоко 1 л
— яйца 10 шт
— хлеб

Ты называешь результат. Каким маршрутом идти и где искать на полках — решает сам магазин (база данных).

● Императивно (Python)

«Как»
  1. выйди из дома
  2. поверни направо, иди 200 м
  3. войди, дойди до холодильника
  4. возьми молоко
  5. иди к стеллажу №3 …

Ты прописываешь каждый шаг сам — циклы, условия, порядок.

💡 Поэтому база сама выбирает оптимальный способ выполнить запрос. А результат SQL — это всегда снова таблица, которую можно вложить в другой запрос.

02 — словарь

Весь язык — это 4 группы команд

Сотни ключевых слов сводятся к четырём задачам: построить структуру, поработать с данными, раздать права и управлять изменениями.

DDL
строим каркас
CREATEALTERDROP

Создаём и меняем сами таблицы — как чертёж дома.

DML
работаем с данными
SELECTINSERTUPDATEDELETE

Читаем, добавляем, правим и удаляем строки внутри таблиц.

DCL
раздаём ключи
GRANTREVOKE

Кому можно смотреть и менять данные, а кому нельзя.

TCL
точка сохранения
COMMITROLLBACKBEGIN

«Сохранить» или «отменить» пачку изменений целиком.

03 — анатомия

Разбираем запрос по строчкам

Нажми на любую строку запроса — покажу, что она делает и какая это кнопка в Excel.

SELECT город, SUM(продажи) -- что выбрать FROM продажи -- откуда WHERE год = 2024 -- фильтр строк GROUP BY город -- группировка HAVING SUM(продажи) > 1000 -- фильтр групп ORDER BY SUM(продажи) DESC -- сортировка LIMIT 10; -- сколько строк

Задача всего запроса: «сумма продаж по городам за 2024 год, оставить города с продажами больше 1000, отсортировать по убыванию, показать топ-10».

04 — аналогия

Всё это ты уже делал руками в Excel

SQL — это те же привычные действия, но автоматически и на миллионах строк. Excel — «грузовичок», SQL — «железнодорожный состав».

SQLТо же самое в Excel
SELECT столбцыОставить только нужные столбцы
WHEREПоставить фильтр на столбец
ORDER BYСортировка А→Я или по числу
GROUP BY + SUMСводная таблица (PivotTable)
JOINВПР / VLOOKUP — подтянуть из другого листа
INSERT INTOДобавить новую строку
UPDATE … SETНайти и заменить значение
CREATE TABLEСоздать новый лист с заголовками

⚙️ Разница: Excel тормозит уже на ~100 тыс. строк, а SQL спокойно работает с миллиардами — и запрос можно сохранить как текст, передать и запустить снова.

05 — главное отличие баз

Хранить по строкам или по колонкам?

Выбери, что ты хочешь сделать с таблицей — и смотри, сколько данных приходится прочитать с диска каждой базе. Подсвеченные ячейки = реально прочитано.

Построчно

PostgreSQL · строки лежат целиком
Имя Город Сумма

Поколоночно

ClickHouse · колонки лежат отдельно
Имя Город Сумма

Аналитике почти никогда не нужны все столбцы — обычно 2 из 20. Поколоночная база читает только эти 2, а построчная вынуждена тащить всю строку целиком.

06 — а почему сжатие ускоряет?

Узкое место — это не процессор, а диск

Кажется, что распаковка только мешает. Но диск читает данные в сотни раз медленнее, чем процессор их распаковывает. Представь грузовой лифт, который возит коробки со склада: лифт медленный, поэтому чем меньше рейсов — тем быстрее.

Без сжатия

лифт возит по 10 коробок
—рейсов лифта

Сжатие 3×

коробок втрое меньше
—рейсов + 5 сек распаковки

Скорости из жизни: NVMe-диск отдаёт ~3–7 ГБ/с, а быстрый алгоритм LZ4 распаковывает ~10–50 ГБ/с. Процессор успевает раньше, чем диск подвезёт данные → сжатие выигрывает. Но если данные уже в оперативке или нужна одна строка — выигрыш пропадает, тут ты был прав.

07 — два инструмента

Касса магазина vs аналитический отдел

Это не «кто лучше». Это разные инструменты под разные задачи.

PostgreSQL

🧾 OLTP · «операционная касса»
  • Много коротких операций каждую секунду
  • UPDATE / DELETE — быстро и привычно
  • Полные транзакции (ACID): надёжно
  • Сложные JOIN — отлично
  • Найти одну запись по ключу — мгновенно
vs

ClickHouse

📈 OLAP · «аналитический отдел»
  • Большая аналитика по миллиардам строк
  • SELECT по огромным таблицам — миллисекунды
  • INSERT пачками, UPDATE — дорого
  • Сильное сжатие: экономит 5–15× места
  • Считать итоги по 2 колонкам из 20 — идеально
🔗 В реальных проектах их не выбирают, а совмещают: PostgreSQL хранит живые данные (заказы, пользователи, статусы), а в ClickHouse льют логи и метрики для дашбордов в BI вроде Superset.
08 — если коротко

Три мысли, которые стоит запомнить

1

SQL = «что», не «как»

Описываешь нужный результат, а база сама придумывает, как его быстро достать. Это и есть декларативность.

2

Строки ⟷ колонки

Нужна одна запись — строки (Postgre). Нужны итоги по миллиардам — колонки (ClickHouse). Читаешь меньше — отвечаешь быстрее.

3

Сжатие — обмен

Меняешь работу процессора на меньшее чтение с диска. Когда диск — узкое место, обмен выгоден.
